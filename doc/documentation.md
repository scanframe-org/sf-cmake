# Documentation

## Compiling

The documentation is compiled by the '**document**' target.

From the command line this is:

```shell
# Linux
 ./build.py -b gnu-debug -n document
 # Windows
 ./build.py -b mingw-debug -n document
 ./build.py -b msvc-debug -n document
 ```

## Convention

This document outlines the conventions for writing project documentation in Markdown files within the source tree.
It is intended to ensure consistency, clarity, and maintainability across all documentation.

### Page Reference / Ranking

A page is referenced by the file's basename, omitting the `.md` extension.
A custom reference name is set with the `ref` key in the front matter at the beginning of the file (see below), for
example `ref: my-file`. The table of contents order is determined by the `rank` key in the front matter.

> **Note**: Files without `rank` are defaulting to a rank of `999`.

Do not put a `{#my-file}` anchor in the heading and do not use Doxygen's `@page` tag in pages having a `ref`.
The anchor is added automatically by the Doxygen input filter, so the Markdown stays clean when rendered
on **GitHub** or **GitLab**.
Writing `{#my-file}` in the heading brings no rendering benefit there: it is shown as literal text.

### Front Matter

A Markdown page starts with a **front matter** block between `---` lines, for example:

```markdown
---
title: Documentation
description: Documentation
ref: documentation
rank: 500 
---
```

The front matter is also understood by other Markdown tools such as **MkDocs**, so the same files can be used with it.

The Doxygen input filter `bin/doxygen-md-filter.py` of the `cmake/lib` submodule processes all `*.md` files
It reads the **front matter** and:

* Only uses the `ref` key: it appends `{#<ref>}` to the first Markdown heading of the page.
* Ignores the `title` and `description` keys; they are informational for other tools.
* Removes the **front matter** block from the output that Doxygen parses.
* Images with a path relative to the file are copied to the accessible location for Doxygen and replaced with a hashed
  name to prevent duplication.
* Fenced PlantUML with an `!include` statement that are being replaced with an embedded version in side the Markdown
  file.

## Subpages & Structure

To provide an entry point to the documentation and help organize content, 
create an `index.md` file in the root of a library or module within the documentation 
section of the source tree.
This file serves as an organizer of the documentation structure for that part of the codebase.
Use the `@subpage` tag within index.md to reference and link to subpages.
This creates a navigable structure in the generated documentation.  
For example:

```
@page my-index My Library

* @subpage my-lib-manual
* @subpage my-lib-module1
* @subpage my-lib-module2
```

## Referencing

### Functions & Methods

Example of referencing namespaced functions:

```markdown
* ::MySpace::calculateOffset
* ::MySpace::clip
* ::getHello
```

When generated:

* ::MySpace::calculateOffset
* ::MySpace::clip
* ::getHello

### Pages

Page are referenced using the previous **front matter** fiels `ref`.

```markdown
\ref main
```
When generated the reference is replaced:


The link to the main page **\ref main**.

## Images

### LibreOffice SVG-files

LibreOffice since it is the only cross-platform application able to export SVG well enough.  
To get a file like this, select all items in the page wit `Ctrl+A` then export the file
with menu `File | Export` and in the save dialog put a checkmark at **Selection** option.
When not, the whole page is put in the resulting SVG-file, which means a lot of white space around it.

### PlantUML

This next SVG-image is generated by PlantUML using Doxygen's PlantUML plugin.
Jar-file latest is automatically fetched and/or downloaded.

The Doxygen filter on Markdown files using `doxygen-md-filter.py` script allows:

- Images with a path relative to the file
- Instead of having `# My Topic {#my-ref}` at the top the reference in now allowed in the front-matter of the file

Each subpage should define its own `@page` tag to enable proper cross-referencing.

## Code Snippets

Source code can be included in a page with Doxygen's `@snippet` command instead of being copied into the Markdown.
This keeps the documentation in sync with the code.

### Marking a Snippet in Source Code

Enclose the part of the source to include between two `//! [<tag>]` markers:

```cpp
//! [Data]
int my_example_var = 0;
//! [Data]
```

### Including a Snippet in Markdown

Reference the copied source file and the snippet tag:

```
@snippet hwl/my-file.cpp Data
```

The file name is `<prefix>/<base name>`, using the `<prefix>` and the base name of the file given to `Sf_AddExamples()`.

### Registering Example Files with CMake

The `Sf_AddExamples(<files> <prefix>)` function, defined in `SfBase.cmake`, makes source files available to Doxygen.
It is called from a `CMakeLists.txt`, for example in `tpl/root/src/CMakeLists.txt`:

```cmake
Sf_AddExamples("hwl/CMakeLists.txt" "hwl")
```

* `<files>`: list of files to register. Relative paths are resolved against the directory of the calling
  `CMakeLists.txt`.
* `<prefix>`: subdirectory in `SF_EXAMPLE_DIR` (default `${CMAKE_BINARY_DIR}/.examples`) which is created when missing.
* Each file is copied to `<SF_EXAMPLE_DIR>/<prefix>/<base name>`. Files with the same base name and prefix overwrite
  each other, so use distinct prefixes.
* The `SF_EXAMPLE_DIR` directory is passed to Doxygen as `EXAMPLE_PATH` via `DG_ExamplePath` in `SfDoxygenConfig.cmake`.
* The copy is done at configure time. After changing a registered source file, re-run the configuration, for example
  with `./build.py -m gnu-debug`, and then build the `document` target.
